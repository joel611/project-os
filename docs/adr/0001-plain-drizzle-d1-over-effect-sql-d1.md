# Build `Db` on plain `drizzle-orm/d1` over a per-request D1 binding, not `@effect/sql-d1` or a module-scope singleton

Better Auth's official `drizzleAdapter` runs queries with `await db.select()...`, which only works against a plain, promise-returning Drizzle instance — not an Effect-native query builder such as one built on `@effect/sql-d1`. This is the same underlying constraint the `effect-drizzle-better-auth` reference repo hit against Postgres (see its `docs/adr/0003-drop-effect-sql-pg-for-shared-postgres-pool.md`): the app's own queries and Better Auth's stock adapter need to share one database handle, and Better Auth's adapter can't be pointed at an Effect-native client.

`Db` (`packages/core/src/libs/db/client.ts`) is instead a `Context.Service` wrapping `drizzle-orm/d1` over a `D1Binding` — a bare `Context.Service` key (`packages/core/src/libs/db/d1-binding.ts`) carrying the raw `D1Database` binding. `Auth` (`packages/core/src/libs/auth/auth.ts`) builds Better Auth's official `drizzleAdapter` directly over that same `Db` instance, so both consumers resolve to the exact same D1 binding through Effect's layer memoization. Every Drizzle call in domain code is wrapped in `Effect.tryPromise` at the call site, matching the reference repo's post-refactor pattern.

This deviates from the reference repo in one further way: `Db.layer` uses a plain `Layer.effect`, not `Effect.acquireRelease`. The reference repo's `pg.Pool` is a long-lived resource that needs an explicit release; D1's binding is not — it's a value handed to the Worker by the runtime for the lifetime of the request, with nothing to open or close. There is nothing to prove shared the way the reference repo's `shared-pool.test.ts` does, so that third test tier is dropped here (see `docs/agents/domain.md` and the Testing Decisions in issue #2).

`Db`/`Auth` are also built **per request**, inside Hono middleware (`apps/api/src/index.ts`), from `c.env.DB` — not once at module scope the way the reference repo's `apps/server/src/effect-runtime.ts` builds its `ManagedRuntime`. `env.DB` only exists inside a request handler on Cloudflare Workers; there is no long-lived process to hang a module-scope singleton off of the way Bun's own server process allows.

Trade-off accepted: `Db`'s query builders are plain promises, not native Effects, so `@effect/sql-d1`'s Effect-native ergonomics are unavailable. A future reader should not "fix" this back toward `@effect/sql-d1` or a shared module-scope runtime — both would either break Better Auth's adapter compatibility or fail outright on the Workers request model.
